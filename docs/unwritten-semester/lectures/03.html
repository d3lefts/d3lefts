SESSION 03 / 14 — FRAME

Requirements that can actually fail

Translate stakeholder intent into testable, versioned traceability.

90 min · lab 2hLECTURE + LAB + ADVERSARIAL CHECKNO PREREQUISITE INSTALLS

The operating principle

A requirement is a testable contract, not a feature wish. “The system shall be reliable” is neither measurable nor assignable. “For synthetic event episodes under dataset D, policy P shall record a per-episode alarm decision and trace its sensor inputs” can be tested, though it still says nothing about a field reliability target.

The essential graph is stakeholder need → requirement → architecture element → verification procedure → evidence → acceptance decision. An orphaned node means the engineering story has broken. An untested requirement is not satisfied because the model looks convincing; a passed unit test is not sufficient to show stakeholder validation.

The six-column contract

Use stable identifiers and record:

  • id: never silently reassign it after revision;
  • shall: one atomic, unambiguous proposition;
  • source: stakeholder, hazard, policy, or governing assumption;
  • rationale: why this condition is necessary;
  • verification: test, analysis, inspection, or demonstration with acceptance conditions;
  • version: the authority and design revision under which it applies.

Separate verification (“Did we build to the stated specification?”) from validation (“Does the specification address the actual need?”). Neither implies the other.

Worked example

Bad: “AURORA sensors should never fail.”

Better synthetic requirement R-03: “For every simulated episode in the archived test trace, the report shall contain the observed channel states A/B/C, the policy identifier, the resulting alarm decision, and an operability flag.”

Test: Parse all rows; assert required columns exist and alarm decisions match the published threshold logic. This verifies the report format and decision calculation, not sensor accuracy or safety.

Lab — build traceability that bites

  1. Inspect templates/requirements.csv and templates/traceability.csv.
  2. Rewrite two deliberately vague requirements into atomic, testable ones.
  3. Create a requirements trace graph that covers all selected claims and acceptance checks.
  4. Add a change event: the decision rule changes from any-positive to quorum. Enumerate the directly and indirectly affected requirements.
  5. Propose one verification test and a separate stakeholder validation question for each altered requirement.

Acceptance artifact: a requirement/verification matrix with no unjustified “verified” labels and explicit orphan reporting.

Adversarial check

Have a reviewer invent a product that satisfies your written requirements but fails the mission. Every successful attack exposes missing validation content. Also test whether two different readers can implement the same “shall” statement without further clarification.

Doctoral extension

Formalize traceability as a typed directed graph. Define a change-impact operator over the graph, and state whether the operator is sound (finds all affected evidence) or complete (does not return irrelevant evidence). These are distinct claims.
