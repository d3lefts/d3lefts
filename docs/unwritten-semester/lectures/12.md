## The operating principle

Research rarely survives contact with revision unless every result knows what it depends on. A source update, policy change, altered requirement, new calibration, or replaced component may invalidate some evidence while leaving the rest usable. **Recertification** is a dependency-selection problem constrained by safety and resource cost.

A simple rule — rerun everything after every change — is defensible but wasteful. Rerun nothing — often unjustified. A useful change-impact analysis tells you which claims require renewed evidence and which remain valid under a demonstrated noninterference argument.

## An evidence dependency graph

Consider `R1: alarm records are traceable`, `R2: policy calculates the declared threshold`, and `R3: anomaly miss rate is below a specified value in model M`. If only the HTML presentation changes, the computation evidence may remain valid. If the alarm policy changes, R2 and R3 must be revisited. If the latent event model changes, R3 must be revisited even when R2 still passes.

Define evidence status as **valid under named versions and assumptions**. Avoid universal “green” indicators without a scope. Version links should point to actual immutable content identifiers, not free-text dates alone.

## Lab — incremental recertification

1. Create a graph of five claims with dependencies on code, environment, policy, parameters, and observed data.
2. Consider three events: (a) CSS edit, (b) quorum-to-any policy edit, (c) changed common-failure probability.
3. For each event, calculate the smallest sound *candidate* impact set by dependency traversal.
4. Specify what proof or test could justify excluding an indirectly linked node from recheck.
5. Measure full-rerun and selective-rerun costs in toy operation units; do not call a selective gain valid until the selection rule is sound.

**Acceptance artifact:** `12-recertification.md` with before/after versions, invalidated nodes, retained evidence rationale, and cost accounting.

## Adversarial check

Construct a change that bypasses your dependency graph: for instance a changed shared environment variable, calibration file, or authority policy. If your detector misses it, the efficiency gain is not a legitimate safety-preserving optimization.

## Doctoral extension

Formalize soundness: under an explicitly defined dependency semantics, all claims whose truth may change must be included in the impact set. Search for sufficient conditions under which a smaller impact operator is provably sound.
