## The operating principle

A best design is best only **relative to an objective function and feasible set**. Systems engineering rarely has a single scalar goal: detection, false alarms, latency, capital cost, lifecycle cost, maintainability, privacy, and failure tolerance often conflict. Reporting one winning architecture without showing the trade space hides the decision.

A design is **Pareto dominated** if another feasible design is no worse on every objective and strictly better on at least one. Pareto efficiency is not global social desirability and does not establish robust performance.

## A minimal trade-space study

For AURORA, compare the `single`, `any`, and `quorum` policies with common synthetic episodes. Track missed events (minimize), false alarms (minimize), per-episode sensor cost (minimize), and operability (maximize). Because `any` and `quorum` use the same three channels, their sensor costs match in the supplied simulator; only their decision behavior differs. The single-channel policy costs less, but uses fewer observations.

Before optimizing, define hard constraints separately from preferences. A simple requirement might be that every reported alarm have a traceable underlying record. A performance target such as miss fraction below 0.05 is a *hypothetical target* until justified by an actual stakeholder and demonstrated with uncertainty.

## Lab — map an actual Pareto frontier

1. Run three policies with the same seed and trial count.
2. Create a table of all four metrics; include numerator and denominator for every fraction.
3. Identify which policies are Pareto dominated in the observed finite sample.
4. Change the cost assigned to sensor B and rerun the trade-space analysis. Does the architecture ranking change?
5. Add a robustness criterion: worst-case performance across a small, declared set of common-failure probabilities, not merely average performance.

**Acceptance artifact:** `08-tradespace.csv` plus a one-page decision note reporting assumptions, constraints, and non-dominated alternatives.

## Adversarial check

Ask whether a design was optimized for the test set it is subsequently “validated” on. Inspect constraint violations separately from score. A tiny gain smaller than measurement or verifier tolerance is at best a tie.

## Doctoral extension

State an optimization problem with decision variables, uncertainty set, and feasible region. Compare a scalarization, epsilon-constraint approach, and robust minimax approach; show one case where weighted sums miss a nonconvex Pareto frontier point.
