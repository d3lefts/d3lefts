## The operating principle

Architecture is a choice about **what can change independently**. A system block diagram shows components; an interface contract says what each component promises; a dependency graph predicts how failures and revisions propagate.

At doctoral level, the difficult part is not drawing the graph. It is distinguishing a causal dependency from mere association, choosing a representation that admits useful proofs or measurements, and knowing when a decomposition hides emergent behavior.

## Three representations for one design

1. **Functional:** observe, classify, notify, record.
2. **Logical:** channel interfaces, policy decision service, event store, operator acknowledgment.
3. **Physical:** sensor hardware, power link, CPU, network, console.

Create a Design Structure Matrix (DSM) where entry `(i,j)=1` means component `i` depends on an interface from `j`. A cluster with dense internal dependencies and sparse external dependencies suggests a module; it does not by itself prove modularity. For each interface, record latency, data type, error semantics, ownership, and revision rules.

## Worked example — mistaken independence

Suppose three channels each have independent local failure probability `p` conditional on a healthy power bus. A shared power-bus failure with probability `q` can disable all channels. Even if local failures are independent, the system-wide probability of total loss is:

```text
P(all unavailable) = q + (1 - q) * p^3
```

A diagram that omits the power bus will suggest `p^3`; that optimistic model is structurally wrong whenever `q > 0`.

1. Use `labs/aurora.py` to simulate three channels with common-mode outage.
2. Compare a diagram assuming independent availability against one with a shared failure node.
3. Build an adjacency matrix for the two designs.
4. List which interfaces must be requalified after changing the shared-power abstraction.
5. Propose a redesigned architecture, and identify a new potential shared failure introduced by the redesign.

## Adversarial check

Look for hidden coupling through power, time, shared training data, administrators, vendor updates, scheduling, and communication. Attack the assumption that two modules are “independent” because they are in different boxes.

## Doctoral extension

Identify a structural property of the architecture (e.g., separator size, cut sets, or observability rank) and establish a bound connecting that property to a measurable mission outcome. Clearly state where approximations enter.
