SESSION 10 / 14 — VERIFY

Safety, security & graceful failure

Connect hazards, attack models, common causes, and recovery.

90 min · lab 3hLECTURE + LAB + ADVERSARIAL CHECKNO PREREQUISITE INSTALLS

The operating principle

Safety analysis asks how people, missions, and environments can be harmed. Security analysis asks how intentional adversaries can cause unacceptable behavior. Resilience asks what the system can continue to do, and how it can recover, after a disturbance. A nominal reliability number cannot replace these questions.

Three methods illuminate different failure mechanisms: a hazard analysis works backward from unacceptable outcomes; a fault tree expresses combinations of events; a failure mode and effects analysis (FMEA) works forward from components. Choose the method that fits the causal question.

Worked failure tree

For AURORA, consider the top event “an anomaly occurs and no alert is generated.” This can arise from total loss of observability, insufficient positive readings, incorrect policy implementation, or failure to deliver an alert. The supplied simulator represents only some of these paths. It does not model downstream notification or human response, so a claim about mission outcome would be unsupported.

Model adversarial inputs as explicit scope changes, not as “just another independent failure probability.” Data spoofing, identity/authority confusion, and time-of-check/time-of-use changes require different controls than random sensor noise.

Lab — trace a hazard to a test

  1. Populate templates/failure-modes.csv with five modes, their causes, effect, detectability, and mitigation.
  2. Draw a fault tree for one top-level hazard. Mark common causes; avoid multiplying probabilities before demonstrating independence.
  3. Propose one prevention control, one detection control, and one recovery control.
  4. Change the simulator's --common-fail parameter and quantify the impact on operability.
  5. Explain which important safety or security failure remains entirely out of scope in your test environment.

Acceptance artifact: 10-hazard-case.md with a fault tree and a hazard-to-requirement-to-evidence chain.

Adversarial check

Use a threat model with attacker capability, controlled inputs, and protected effects. A successful defense against a non-executable attack is not evidence of protection against an executable one. Challenge assumptions that data are truthful, current, or issued by the expected authority.

Doctoral extension

Give a bound on a top-event probability from a fully stated fault tree, then identify where common-cause dependence destroys the bound. Distinguish a probabilistic risk estimate from a safety guarantee.
